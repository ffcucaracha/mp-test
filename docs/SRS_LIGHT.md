# AgroConnect MVP — SRS Light

**Статус:** Draft / Hypothesis Baseline  
**Версия:** 0.1  
**Дата:** 2026-09-06

## 1. Назначение документа

Этот документ фиксирует исходную продуктовую рамку AgroConnect MVP перед началом активной реализации. Он объединяет:

- обязательное функциональное ядро из конкурсного брифа;
- тезисы со стартовой встречи хакатона;
- роли и стейкхолдеров;
- базовые пользовательские сценарии;
- гипотезы жюри/организаторов;
- собственные продуктовые гипотезы команды;
- требования к сбору метрик для последующей проверки гипотез.

Документ не является финальным backlog. Его задача — сохранить исходную точку и отделить обязательные требования от экспериментальных идей.

---

## 2. Контекст продукта

AgroConnect MVP — мобильный сервис для сельхозтоваропроизводителей, прежде всего растениеводов, которые работают с полями и управляют ими.

Исходная идея организаторов — проверить, нужен ли аграриям не очередной мессенджер, а комбинация:

> **рабочий дневник + профессиональная социальная площадка для обмена опытом**

Пользователь должен иметь возможность быстро показать, что происходит на поле, увидеть состояние соседних хозяйств и получить обратную связь от других аграриев.

Главная бизнес-цель MVP — не максимальное количество функций, а возможность после хакатона отдать прототип реальным хозяйствам, снять метрики и подтвердить либо опровергнуть продуктовые гипотезы.

---

## 3. Цели MVP

### 3.1. Бизнес-цели

1. Проверить, существует ли практическая ценность у специализированной социальной сети для аграриев.
2. Проверить, готовы ли фермеры делиться информацией о своих полях, проблемах и результатах.
3. Проверить, какие функции создают причину возвращаться в приложение.
4. Проверить, какие локальные и профессиональные сценарии дают AgroConnect преимущество перед обычными мессенджерами и соцсетями.
5. Собрать количественные и качественные метрики для принятия решения о дальнейшей разработке продукта.

### 3.2. Цели хакатонной версии

- запустить прототип на Android-устройстве;
- показать end-to-end сценарий взаимодействия пользователя с приложением и сервером;
- встроить 2–3 проверяемые гипотезы;
- фиксировать действия пользователей;
- подготовить основу для тестирования на реальных фермерах.

## 4. Stakeholders и роли

### ST-01. Фермер / растениевод

Основной пользователь системы.

Характеристики:

- управляет одним или несколькими полями;
- работает непосредственно в поле либо принимает оперативные решения по хозяйству;
- использует смартфон как основной мобильный инструмент;
- заинтересован в состоянии культур, погоде, заболеваниях, обработках и опыте соседних хозяйств.

### ST-02. Пчеловод

Дополнительная продуктовая роль, не заданная в обязательном ядре конкурса.

Интересы:

- расположение пасек;
- информация о соседних полях;
- предупреждения о применении пестицидов;
- погодные угрозы;
- взаимодействие с растениеводами поблизости.

### ST-03. Фермер-сосед

Контекстная роль того же фермера, когда он взаимодействует с другими хозяйствами поблизости.

Может:

- получать локальные уведомления;
- видеть публикации соседей;
- реагировать и комментировать;
- предупреждать других участников;
- запрашивать доступ к более подробной информации о хозяйстве.

### ST-04. Агроном / опытный сельхозспециалист

Может выступать как:

- автор экспертных комментариев;
- пользователь функций диагностики;
- участник проверки рекомендаций и ML-подсказок.

### ST-05. Владелец продукта / группа компаний

Интересы:

- проверить рыночную гипотезу;
- определить наиболее востребованный функционал;
- собрать метрики;
- решить, стоит ли развивать AgroConnect дальше.

### ST-06. Жюри хакатона

Временный stakeholder MVP.

Интересы:

- установить приложение;
- пройти ключевые пользовательские сценарии;
- увидеть продуктовые эксперименты;
- оценить удобство, понятность и практическую ценность.

## 5. UX- и эксплуатационные ограничения

Приложение проектируется прежде всего для смартфона и работы в полевых условиях.

Базовые UX-принципы:

- минимум текста;
- крупные интерактивные элементы;
- визуальная подача;
- понятность при ярком солнечном свете;
- географический контекст как часть интерфейса;
- быстрые действия одной рукой;
- отсутствие критической зависимости от сложного ввода текста.

Для жюри приоритетен Android-телефон. APK обозначен как основной ожидаемый результат, но технология реализации может быть альтернативной, если приложение удобно работает на мобильном устройстве.

## 6. Обязательное функциональное ядро из брифа

### FR-01. Профиль агрария

Система должна отображать профиль пользователя минимум со следующими атрибутами:

- имя;
- специализация;
- регион.

### FR-02. Географическая привязка хозяйства

Пользователь должен иметь возможность указать местонахождение поля.

Возможные способы:

- точка на карте;
- полигон;
- геометка фотографии;
- другой способ геопривязки.

### FR-03. Публикации с поля

Пользователь должен иметь возможность создать публикацию с фото или видео и указать статус, например:

- посев;
- всходы;
- цветение;
- проблема;
- урожай.

### FR-04. Лента чужих полей

Пользователь должен иметь возможность просматривать публикации других хозяйств.

### FR-05. Социальное взаимодействие

Для публикации должны быть доступны:

- реакция;
- комментарий.

Тип реакции может использоваться как часть эксперимента.

## 7. Базовые пользовательские сценарии

### UC-01. Показать состояние поля

**Актор:** растениевод.

1. Пользователь открывает своё поле.
2. Делает фотографию или выбирает изображение.
3. Указывает статус события.
4. При необходимости добавляет комментарий.
5. Публикует запись.
6. Запись становится доступна другим участникам.

### UC-02. Посмотреть публикации соседей

**Актор:** растениевод.

1. Пользователь открывает ленту или карту.
2. Видит публикации других хозяйств.
3. Открывает публикацию.
4. Оставляет реакцию или комментарий.

### UC-03. Получить совет по проблеме

**Актор:** растениевод.

1. Пользователь фотографирует проблему на растении.
2. Создаёт публикацию со статусом «Проблема».
3. Другие пользователи видят запись.
4. Пользователь получает комментарии или рекомендации.

### UC-04. Посмотреть профиль другого агрария

**Актор:** любой пользователь.

1. Пользователь открывает автора публикации.
2. Видит имя, специализацию и регион.
3. При наличии разрешения может перейти к информации о хозяйстве.

# 8. Гипотезы жюри / организаторов

Этот раздел отделяет исходные гипотезы конкурса от собственных идей команды.

## JH-01. Аграриям нужен профессиональный рабочий дневник + площадка обмена опытом

**Гипотеза:** специализированный продукт для аграриев создаёт большую ценность, чем очередной универсальный мессенджер.

**Как проверить:** дать пользователям возможность публиковать состояние полей и получать обратную связь.

**Признаки подтверждения:** повторное использование, публикации, реакции, комментарии, субъективная оценка полезности.

## JH-02. Фермерам удобно быстро показывать проблему через фото, а не описывать её текстом

**Гипотеза:** визуальный сценарий снижает порог публикации и общения в поле.

**Как проверить:** сценарий «сфотографировать → указать статус → опубликовать».

## JH-03. География повышает ценность контента

**Гипотеза:** информация от хозяйств поблизости более полезна, чем просто хронологическая лента.

**Как проверить:** геолента, карта или фильтрация публикаций по расстоянию.

## JH-04. Пользователи готовы делиться информацией о своих полях

**Гипотеза:** фермеры готовы публиковать данные о состоянии полей, проблемах, урожае и других событиях.

Это открытая гипотеза, прямо обсуждавшаяся на стартовой встрече.

**Как проверить:** доля пользователей, создающих публикации и поля, и качественная обратная связь о приватности.

## JH-05. Простые социальные реакции можно оптимизировать экспериментом

**Гипотеза:** формат реакции влияет на вовлечённость.

**Эксперимент:** A/B-тест, например «👍» против «🌱» или «🔥».

**Метрики:** reaction rate, comment rate, conversion to interaction.

## JH-06. Ограниченная функция может стимулировать вклад пользователя

**Гипотеза:** пользователь готов совершить целевое действие ради доступа к дополнительной функции.

**Пример эксперимента:** архив старых публикаций доступен после нескольких собственных публикаций либо пользователь кликает на teaser «Хотите видеть фото за прошлый год?».

**Метрики:** CTR, conversion to target action.

## JH-07. Автоматический анализ фото может быть полезным дополнением

**Гипотеза:** даже предварительная подсказка по изображению повышает ценность публикации проблемы.

Для MVP допускается упрощённая реализация или имитация результата.

## JH-08. Погодные триггеры могут создавать полезные событийные уведомления

**Гипотеза:** пользователь получает больше пользы от контекстного уведомления, если оно связано с состоянием конкретного поля.

Пример: дождь, град или заморозок в сочетании со статусом культуры.

## JH-09. Геймификация может повысить вовлечённость

**Гипотеза:** серии дней, рейтинги или награды могут стимулировать публикации и ответы.

# 9. Собственные продуктовые гипотезы

## H-01. Географически релевантные предупреждения ценнее обычной ленты

**Гипотеза:** фермеру полезнее получать оперативную информацию от хозяйств поблизости, чем просто видеть общий поток публикаций.

Возможные события:

- заболевания растений;
- применение пестицидов;
- заморозки;
- локальные угрозы.

Предварительный радиус проверки: **100–200 км**, но расстояние должно быть параметром, а не жёстким правилом.

**Метрики:**

- notification open rate;
- переход к публикации или карте;
- комментарии и реакции;
- отключение уведомлений.

## H-02. Предупреждения о заболеваниях растений создают сетевую ценность

**Гипотеза:** если один растениевод обнаружил заболевание, соседние хозяйства захотят узнать об этом заранее.

Сценарий:

`Фото проблемы → определение/указание болезни → публикация → уведомление соседних хозяйств`

**Метрики:**

- количество публикаций с признаком угрозы;
- использование действия «предупредить соседей»;
- открываемость уведомлений;
- дальнейшие действия пользователей.

## H-03. Предупреждения о пестицидах особенно ценны для пчеловодов

**Гипотеза:** AgroConnect может создавать практическую ценность на стыке растениеводства и пчеловодства.

Сценарий:

`Растениевод планирует обработку → указывает поле и время → пчеловоды поблизости получают предупреждение`

Ценность для пчеловода — возможность вовремя защитить пасеку.  
Ценность для растениевода — снижение конфликтов с соседними пасечниками.

**Метрики:**

- доля пчеловодов, включивших такие уведомления;
- notification open rate;
- переход к деталям обработки;
- запрос связи с владельцем поля;
- оценка полезности.

## H-04. Пчеловод — полноценный пользователь AgroConnect

**Гипотеза:** продукт может быть полезен не только растениеводам, но и участникам локальной агроэкосистемы.

Для MVP проверяется один конкретный cross-role сценарий:

> **растениевод ↔ пчеловод**

Потенциальные функции:

- пасека на карте;
- предупреждения о пестицидах;
- локальные погодные угрозы;
- события поблизости;
- связь с владельцем поля.

## H-05. ML-распознавание фотографии снижает порог публикации проблемы

**Гипотеза:** фермеру проще сфотографировать проблему и получить предварительную подсказку, чем формулировать описание вручную.

Сценарий:

`Фото → ML предлагает «Похоже на ...» → пользователь подтверждает или исправляет → публикация`

**Метрики:**

- diagnosis_started;
- доля принятых подсказок;
- доля исправлений;
- доля публикаций, созданных через ML-flow;
- пользовательская оценка полезности.

## H-06. ML полезнее как помощник, а не как окончательный эксперт

**Гипотеза:** безопаснее и полезнее использовать ML как старт социальной коммуникации.

Не:

> «ИИ поставил диагноз».

А:

> «Похоже на ржавчину. Опубликовать вопрос соседям?»

Цепочка:

`Фото → ML-подсказка → локальное предупреждение → обсуждение`

## H-07. Предупреждение о заморозках полезно только в контексте конкретного поля

**Гипотеза:** уведомление «будет −2 °C» менее ценно, чем сообщение, привязанное к культуре и полю.

Пример:

> «На вашем поле с картофелем ожидается заморозок».

Ценность создаёт комбинация:

`геопозиция + культура/статус поля + погода`

## H-08. История севооборота повышает ценность AgroConnect как рабочего дневника

**Гипотеза:** пользователь будет возвращаться в приложение ради собственной истории хозяйства, а не только социальной ленты.

Минимальная модель:

`поле + год + культура`

Пример:

`2024 — пшеница → 2025 — рапс → 2026 — ячмень`

**Метрики:**

- доля пользователей, заполнивших историю;
- повторные просмотры;
- количество добавленных сезонов.

## H-09. Пользователю нужна собственная статистика хозяйства

**Гипотеза:** персональная аналитика повышает ценность рабочего дневника.

Возможные показатели MVP:

- количество полей;
- суммарная площадь;
- культуры по годам;
- количество публикаций;
- выявленные проблемы;
- полученные советы.

## H-10. Пользователи готовы делиться деталями хозяйства только с доверенными соседями

**Гипотеза:** бинарная модель «всё публично / всё скрыто» слишком грубая.

Нужен контролируемый доступ.

## H-11. Механика «Попроситься в гости» снижает барьер приватности

Сценарий:

1. Пользователь открывает профиль соседа.
2. Подробный план хозяйства скрыт.
3. Нажимает **«Попроситься в гости»**.
4. Владельцу приходит запрос.
5. Владелец разрешает или отклоняет доступ.
6. После разрешения становятся доступны дополнительные данные.

Возможные уровни доступа:

- публично — только публикации;
- соседям — приблизительная география;
- после разрешения — поля, севооборот и подробности.

**Метрики:**

- visit_requested;
- approval rate;
- rejection rate;
- просмотры хозяйства после одобрения.

## 10. Сквозная продуктовая гипотеза

Собственные идеи сводятся к следующей формулировке:

> **AgroConnect полезен не как социальная сеть сама по себе, а как географическая сеть взаимопомощи между соседними сельхозпроизводителями.**

Первый контур ценности:

`поле → соседи → проблема → фото/ML → предупреждение → обсуждение → доверенный доступ`

Второй контур ценности:

`моё поле → севооборот → история → статистика → рабочий дневник`

Таким образом, у пользователя появляются две независимые причины возвращаться:

1. **Что происходит вокруг меня?**
2. **Что происходит в моём хозяйстве?**

## 11. Требования к аналитике и сбору метрик

### FR-METRICS-01. Event logging

Система должна сохранять пользовательские события, необходимые для проверки гипотез.

Минимальный набор событий:

```text
user_selected
field_created
field_viewed
post_created
post_viewed
reaction_added
comment_created

diagnosis_started
diagnosis_accepted
diagnosis_rejected

alert_created
alert_received
alert_opened

visit_requested
visit_approved
visit_rejected

crop_rotation_viewed
statistics_viewed
```

Минимальная структура события:

```text
event_name
user_id
timestamp
properties JSON
```

### FR-METRICS-02. Экспериментальные группы

Система должна позволять сохранять вариант эксперимента пользователя, например:

```text
experiment_name
variant
user_id
```

Это необходимо для A/B-тестов реакций и других вариантов интерфейса.

### FR-METRICS-03. Простая аналитика MVP

Для хакатонной версии достаточно:

- event log в PostgreSQL;
- SQL-запросов или простого admin/statistics endpoint;
- необязательно строить полноценную BI-систему.

| Farm Diary | история поля, севооборот |
| Trusted Access | «попроситься в гости», права просмотра |
| Personal Analytics | собственная статистика |
| Experiment Analytics | event logging, продуктовые метрики, A/B |

---

## 13. Что пока не является решением

На этой стадии **не зафиксировано**, какие именно собственные гипотезы войдут в MVP.

До формирования backlog необходимо отдельно определить:

- какие 2–3 гипотезы являются главными;
- какие функции нужны для их проверки;
- какие данные нужны для метрик;
- какие функции сознательно уходят в backlog;
- какой happy path должен быть готов первым.

Предварительно наиболее сильный набор для обсуждения:

1. локальные предупреждения;
2. растениевод ↔ пчеловод / предупреждения о пестицидах;
3. фото → ML-подсказка → предупреждение соседей.

Севооборот, личная статистика и доверенный доступ «Попроситься в гости» остаются кандидатами второго приоритета до финальной приоритизации.

---

## 14. Следующий шаг

На основе этого документа требуется подготовить отдельный backlog MVP с приоритетами:

- **Must have** — обязательное ядро и функции, без которых нельзя проверить выбранные гипотезы;
- **Should have** — усиливают основной сценарий;
- **Could have** — демонстрационные или расширяющие идеи;
- **Won't have now** — сознательно отложенные функции.

После выбора 2–3 основных гипотез SRS Light должен быть обновлён до версии 0.2 с уточнёнными user flows, критериями приёмки и метриками успеха.
