# AgroConnect MVP — Product Decisions

**Статус:** Approved scope for MVP  
**Версия:** 1.0  
**Дата:** 2026-09-06

## 1. Назначение документа

Документ фиксирует принятые продуктовые решения для хакатонной версии AgroConnect MVP: какие гипотезы проверяем, какие функции входят в MVP, какие оставляем в backlog, какие метрики собираем и где проходит граница реализации.

Базовый SRS Light хранится отдельно в `docs/SRS_LIGHT.md`. Этот документ является следующей стадией: не перечнем идей, а зафиксированным scope.

---

## 2. Продуктовая формулировка

> **AgroConnect — географическая сеть взаимопомощи сельхозпроизводителей, которая объединяет рабочий дневник хозяйства, локальные предупреждения и обмен опытом между соседями.**

Ключевая ценность строится вокруг двух контуров:

1. **Что происходит вокруг меня?** — локальная лента, соседи, предупреждения о болезнях, обработках и погодных рисках.
2. **Что происходит в моём хозяйстве?** — поля, культура, история севооборота, профиль и личная статистика.

---

## 3. Основные продуктовые гипотезы MVP

### H1. Географически релевантная агросеть полезнее обычной социальной ленты

**Гипотеза:** фермеру ценнее получать информацию от релевантного круга пользователей и хозяйств вокруг него, чем читать общую хронологическую ленту.

Проверяем через:

- географическую привязку полей;
- радиус получения новостей;
- радиус распространения публикаций и предупреждений;
- механику соседей;
- локальную ленту;
- ранжирование публикаций.

### H2. Локальные предупреждения создают практическую ценность

**Гипотеза:** пользователь готов использовать AgroConnect как рабочий инструмент, если получает своевременные предупреждения о событиях, способных повлиять на его хозяйство.

Типы событий MVP:

- заболевание / проблема на поле;
- обработка пестицидами;
- погодный риск, прежде всего заморозки.

### H3. Личный рабочий дневник создаёт ценность даже без развитой социальной сети

**Гипотеза:** если AgroConnect хранит историю полей и культур, пользователь получает самостоятельную причину возвращаться в приложение.

Проверяем через:

- поля;
- текущую культуру;
- историю севооборота;
- собственную статистику.

### H4. Контролируемая приватность повышает готовность делиться данными о хозяйстве

**Гипотеза:** пользователи охотнее заполняют реальные данные о своих полях, если сами контролируют, кто может видеть подробности.

Для этой гипотезы в MVP реализуется A/B-эксперимент приватности полей.

## 4. Модель пользователя

В MVP **не вводятся бизнес-роли `farmer` / `beekeeper`**.

Пользователь — единая сущность. Пчеловодство является дополнительным признаком / направлением деятельности.

Минимальный профиль:

```text
User
- id
- name
- region
- specialization
- farm_name
- bio
- is_beekeeper: bool
- news_radius_km
- broadcast_radius_km
```

Если пользователь отмечает **«У меня есть пасека»**, становится доступен дополнительный блок:

```text
Apiary
- id
- owner_id
- name
- latitude
- longitude
- alert_radius_km
```

Это позволяет одному человеку одновременно быть растениеводом и пчеловодом.

## 5. Scope MVP

## 5.1. MUST — обязательно реализовать

### M1. Профиль пользователя

Минимум:

- имя;
- регион;
- специализация;
- хозяйство;
- краткое описание;
- признак «Есть пасека»;
- полнота профиля.

### M2. Поля и географическая привязка

Пользователь может:

- создать поле;
- указать название;
- указать культуру;
- поставить точку на карте;
- открыть поле на карте.

Полигон поля не является обязательным для MVP.

### M3. Настройки географического радиуса

Пользователь может отдельно задать:

- радиус получения новостей;
- радиус распространения своих предупреждений.

Предлагаемые варианты:

```text
25 / 50 / 100 / 200 км
```

Радиус хранится как пользовательская настройка, а не как жёсткое системное значение.

### M4. Публикации с поля

Публикация содержит:

- автора;
- поле;
- фото;
- статус;
- необязательный текст;
- географическую привязку;
- дату и время.

Минимальные статусы:

```text
посев
всходы
цветение
проблема
урожай
обработка
```

Фото — обязательный медиасценарий MVP. Видео оставляется в backlog.

### M5. Лента публикаций

Пользователь видит публикации других участников.

Лента должна учитывать:

- расстояние;
- свежесть;
- оценку публикации.

Сложная рекомендательная модель не требуется.

### M6. Реакции

В продукте фиксируется собственная аграрная механика реакций:

- **здоровый колосок** — положительная оценка `+1`;
- **увядший колосок** — отрицательная оценка `-1`.

Реакции используются для:

- вовлечения;
- вычисления score публикации;
- формирования репутации пользователя;
- продуктовых метрик.

Форма реакций в MVP не участвует в A/B-тестировании.

### M7. Комментарии

Под публикацией доступны обычные текстовые комментарии.

Голосовые комментарии — backlog.

### M8. Механика соседей

Сосед — явная связь между пользователями и не обязан определяться географией.

Пользователь может:

- добавить другого пользователя в соседи;
- удалить из соседей;
- видеть количество соседей;
- переходить к профилю соседа.

Географическая близость и социальное соседство — разные механики.

### M9. Предупреждения

Общий механизм предупреждений должен поддерживать минимум три типа:

```text
disease
pesticide
weather
```

Каждое предупреждение связано с:

- автором / источником;
- полем или точкой;
- типом;
- радиусом распространения;
- временем;
- полезной нагрузкой.

### M10. Пестициды и пчеловоды

Пользователь с включённым признаком «Есть пасека» может добавить одну или несколько пасек.

Растениевод может создать событие о планируемой обработке поля.

Пчеловод получает предупреждение, если пасека попадает в радиус события.

Из предупреждения доступны действия:

- открыть поле / публикацию;
- открыть профиль владельца;
- перейти к доступному контакту владельца.

Отдельный чат не реализуется.

### M11. Интеграция с погодой

Для поля по координатам запрашивается прогноз погоды.

MVP использует погоду только как источник событийного триггера, например:

> «На вашем поле ночью ожидается заморозок».

Отдельный сложный погодный экран не нужен.

### M12. Севооборот

Для каждого поля хранится история культур по годам.

```text
CropSeason
- field_id
- year
- crop
```

Пользователь может:

- посмотреть историю;
- добавить запись за год.

Рекомендации по оптимальному севообороту в MVP не входят.

### M13. Геймификация

В MVP ограничиваемся простыми показателями:

- полнота профиля;
- количество соседей;
- серия недель активности;
- репутация по реакциям.

Не строится отдельная игровая подсистема.

### M14. Сбор продуктовых событий

Система должна фиксировать действия пользователей, необходимые для проверки гипотез.

Минимальный event log:

```text
user_selected
profile_updated
field_created
field_location_added
field_opened
crop_rotation_added
post_created
post_viewed
reaction_added
comment_created
neighbor_added
alert_created
alert_received
alert_opened
weather_alert_opened
apiary_created
owner_contact_opened
visit_request_sent
visit_request_approved
visit_request_rejected
private_field_viewed
public_field_viewed
ml_started
ml_result_shown
ml_result_accepted
ml_result_rejected
```

Событие содержит минимум:

```text
event_name
user_id
timestamp
properties JSON
experiment_variant nullable
```

### M15. Внутренний экран метрик

Полноценная админ-панель не требуется.

Достаточно внутреннего экрана `/internal/metrics`, показывающего:

- число пользователей;
- созданные поля;
- заполненную географию;
- публикации;
- просмотры;
- реакции;
- комментарии;
- предупреждения и open rate;
- запросы «в гости» и approval rate;
- использование ML;
- использование севооборота.

Доступ может быть защищён простым техническим механизмом.

---

## 5.2. SHOULD — реализовать, если базовый happy path стабилен

### S1. ML-распознавание фото

Сценарий:

```text
фото растения
→ ML/AI-подсказка
→ «Похоже на ...»
→ подтвердить / исправить
→ создать публикацию «Проблема»
→ при необходимости предупредить соседей
```

ML не позиционируется как окончательный диагноз.

Ключевой смысл — сократить путь от обнаружения проблемы до публикации и предупреждения.

### S2. Простая собственная статистика пользователя

Минимум:

- количество полей;
- количество публикаций;
- текущие культуры;
- количество предупреждений;
- репутация;
- серия активности.

### S3. Полигон поля

Если выбранная библиотека карт позволяет реализовать без существенных затрат, добавить рисование границы поля.

Иначе точка остаётся достаточной для MVP.

---

## 5.3. COULD — только при наличии времени

- отдельная вкладка карты с публикациями;
- дополнительные типы предупреждений;
- расширенная статистика;
- красивые достижения;
- локальные push-уведомления;
- дополнительные настройки приватности;
- несколько пасек на пользователя с индивидуальными радиусами;
- расширенная карточка погоды.

---

## 5.4. WON'T / Backlog

До финала хакатона сознательно не реализуем:

- полноценный чат;
- голосовые комментарии;
- полноценный видеопайплайн;
- сложную ACL-модель;
- группы и групповые чаты;
- платежи;
- production-grade push-инфраструктуру;
- сложную систему достижений;
- собственное обучение большой ML-модели;
- полноценные агрономические рекомендации по севообороту;
- сложную рекомендательную систему ленты;
- enterprise-grade admin panel.

---

## 6. A/B-эксперимент: приватность поля

### 6.1. Проверяемая гипотеза

> Пользователи охотнее заполняют реальные данные о своих полях, если сами контролируют доступ к подробной информации о хозяйстве.

### 6.2. Variant A — открытые поля

Другой пользователь сразу видит:

- точное расположение;
- культуру;
- историю севооборота;
- связанные публикации.

### 6.3. Variant B — контролируемый доступ

Без разрешения другой пользователь видит:

- профиль владельца;
- публичные публикации;
- приблизительную информацию о хозяйстве.

Для просмотра деталей доступно действие:

> **Попроситься в гости**

После одобрения становятся доступны:

- точное расположение поля;
- культура;
- севооборот;
- связанные данные поля.

### 6.4. Минимальная модель доступа

```text
Field
- visibility_variant: public | controlled

FieldVisitRequest
- id
- requester_id
- owner_id
- field_id nullable
- status: pending | approved | rejected
- created_at
- resolved_at nullable
```

Сложная ACL-модель не требуется.

### 6.5. Метрики эксперимента

Основные события:

```text
field_created
field_location_added
crop_rotation_added
field_profile_opened
visit_request_sent
visit_request_approved
visit_request_rejected
private_field_viewed
public_field_viewed
```

Ключевые показатели:

- доля пользователей, создавших поле;
- доля добавивших точную географию;
- доля заполнивших севооборот;
- число запросов «в гости»;
- approval rate;
- просмотры подробностей после одобрения.

### 6.6. Интерпретация

Если пользователи Variant B заметно чаще заполняют реальные сведения о поле, это является аргументом в пользу контролируемой приватности.

Если запросов «в гости» мало, но заполненность данных выше, контроль приватности всё равно может быть ценен сам по себе.

Если различий нет, гипотеза считается не подтверждённой и сложную модель приватности развивать не следует без дополнительных качественных интервью.

---

## 7. Гипотеза-приманка из брифа

Для закрытия конкурсной идеи о псевдоплатной / ограниченной функции реализуется дешёвый teaser, например:

> **«Открыть расширенную статистику хозяйства»**

или

> **«Посмотреть полную историю поля за прошлые годы»**

Клик логируется как событие. Реальная платёжная логика не нужна.

Минимальные метрики:

```text
premium_teaser_shown
premium_teaser_clicked
```

## 8. Приоритеты реализации

### P0 — без этого MVP нельзя сдавать

- профиль;
- поля;
- география;
- публикации с фото;
- лента;
- реакции;
- комментарии;
- event logging;
- базовые метрики;
- A/B-приватность;
- работающий Android build / мобильный сценарий.

### P1 — основная продуктовая ценность

- радиусы новостей и трансляции;
- соседи;
- предупреждения;
- пестициды + пасека;
- погода / заморозки;
- севооборот;
- простая геймификация.

### P2 — сильные усилители демо

- ML по фото;
- собственная статистика;
- полигон поля;
- карта публикаций;
- дополнительные достижения.

## 9. Критерий завершённости MVP

MVP считается готовым к демонстрации, если можно пройти сквозной сценарий:

1. выбрать / создать пользователя;
2. заполнить профиль;
3. создать поле и привязать его к карте;
4. указать культуру и севооборот;
5. создать публикацию с фото;
6. увидеть её в ленте другого пользователя;
7. оставить реакцию и комментарий;
8. добавить пользователя в соседи;
9. создать предупреждение о проблеме или обработке;
10. получить его другим пользователем в нужном радиусе;
11. для пчеловода получить предупреждение об обработке возле пасеки;
12. пройти сценарий A/B-приватности и «попроситься в гости»;
13. увидеть агрегированные метрики экспериментов;
14. установить и запустить приложение на Android-устройстве.

ML не блокирует сдачу, если основной happy path стабилен.
